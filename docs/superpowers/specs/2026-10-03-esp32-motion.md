# Spec: motion detector on the LD2410C data (ESP32 MVP)

Date: 2026-10-03. Owner: Andrii. Status: approved in brainstorming (2026-10-03, "все a").

## Context

The LD2410C reports, per data frame (about 10 Hz), a target state (none / moving / still / both),
the moving target distance and energy, the still target distance and energy, and in engineering
mode the energy per gate (`components/core/ld2410_frame.h`). The MVP records the raw frames but
has no notion of an "event". BACKLOG: "Radar motion detector".

## Decisions (owner, brainstorming 2026-10-03)

1. **Motion = the module's moving target, filtered**: a frame counts as "moving" when the moving
   bit of the target state is set, the moving distance is inside a zone `[min, max]` and the
   moving energy is at least a threshold. An event **starts** when moving frames persist for at
   least `start_ms` and **ends** after `end_ms` without a moving frame. (Option b, an own detector
   on the per-gate energies with a learned background, and option c, presence including still
   targets, were not chosen.)
2. **Events go to the recording, the live page and `/log`**: a new record type `motion` (start
   and end), a motion indicator and the last 10 events on the live page, one `/log` line per
   start and end; the host exports the events as a CSV. The recording protocol stays v3: a host
   that does not know the type keeps it raw (`UnknownRec`).
3. **Zone and thresholds are set on the `/ld2410` page (AP only), stored in NVS**; changes are
   logged.
4. **No notifications outside the board** (phone push, messengers) now: BACKLOG.

## Agent choices (documented, adjustable on the page)

Defaults: zone 100..500 cm, energy >= 30, `start_ms` 1000, `end_ms` 3000, detector enabled.
Limits: zone 0..900 cm with min < max; energy 0..100; `start_ms` 100..10000; `end_ms`
500..60000; enabled 0/1. Defaults are a starting point, to be tuned on the bench (VERIFY).

## Requirements

### R1. Detector (core, C11, host-tested): `components/core/motion_det.[ch]`
- Config struct (fields above) with `motion_cfg_defaults()` and `motion_cfg_check()`.
- `motion_det_step(det, cfg, const ld_data_t *d_or_NULL, uint64_t now_us, motion_ev_t *ev)`:
  one call per decoded frame; `NULL` = no data (link lost), treated as a non-moving frame.
  Returns `MOTION_EV_NONE`, `MOTION_EV_START` or `MOTION_EV_END` and fills `ev`.
- States: IDLE -> PENDING (first moving frame, onset time stored) -> ACTIVE when
  `now - onset >= start_ms` with every frame since onset moving (a non-moving frame in PENDING
  returns to IDLE) -> ACTIVE stays while moving frames arrive; END when
  `now - last_moving >= end_ms`, checked on every call (also on non-moving and NULL frames).
- During PENDING/ACTIVE track: onset time, last moving time, max energy and the distance at
  that max, min and max moving distance.
- Event fields: `event_no` (u32, counts started events since boot, first is 1), onset ESP time
  (us), duration ms (END: last moving - onset; START: 0), max energy, distance at max energy,
  min/max distance (START: values seen during PENDING).
- `enabled = 0`: no new events; an ACTIVE event is ended on the next call (END emitted).
- Config change while ACTIVE/PENDING: the new config applies from the next frame.
- uint64 time arithmetic only; no wrap concerns (esp_timer is 64-bit), but `now < onset` (must not
  happen) is treated as 0 elapsed.

### R2. Record type 4 `motion` (core + host + shared vectors)
- `REC_TYPE_MOTION 4u`, payload 28 B, little-endian: `event_no u32, kind u8 (1 start, 2 end),
  max_energy u8, dist_cm u16 (distance at max energy), min_dist_cm u16, max_dist_cm u16,
  onset_esp_us u64, duration_ms u32, reserved u8[4] = 0`.
- The record header time is the push time (keeps the ring's time order); the onset is in the
  payload. Decoder rejects a wrong length, nonzero reserved bytes and a kind other than 1/2
  (-EBADMSG).
- Host `host/ld2410_rec.py`: decode type 4 (`MotionRec`), `info` counts motion events, a CSV export
  `--motion` (one row per END record, plus START rows without an END at the end of the file
  marked open; columns: event_no, start_utc, end_utc, duration_s, max_energy, dist_m, min_dist_m,
  max_dist_m, boot); UTC via the existing time mapping of the onset ESP time. Vectors in
  `esp32/tests/vectors/` (generator `gen_vectors.py`), used by the C and Python tests.

### R3. Integration (esp32/main)
- The LD2410C task runs the detector on every decoded data frame (and once per second with
  `NULL` while no frame arrives, so an event ends when the link is lost).
- On START/END: push a `motion` record into the ring; log one line
  (`motion start #N at X.XX m, energy E` / `motion end #N, D.D s, X.XX m (min..max), energy E`).
- Keeps the last 10 events (started; END fills duration) for the page, under a mutex.
- Config: NVS namespace `motion` (one blob or keys), loaded at start (defaults if absent or out
  of range), replaced atomically from the page.

### R4. Live page and endpoints
- Snapshot JSON gains `"motion":{"en":0|1,"active":0|1,"n":<event_no of latest>,
  "dist":<cm of current moving target or null>}`; `SNAPSHOT_JSON_MAX` still holds (host test).
- `GET /motion/events` (STA and AP, like the live page): JSON array of the last 10 events,
  newest first, each `{no, onset_ms_ago, dur_ms (null while active), energy, dist, min, max}`.
- Live page: a "Motion" card: indicator (active / idle / disabled), current distance, and the
  list, refetched when `n` or `active` changes.

### R5. Settings on `/ld2410`
- A "Motion detector" section with the six fields and Save (separate form, `POST
  /ld2410/motion`, AP only, Origin check like the other POSTs, form-urlencoded, length-limited,
  parsed and range-checked in core `motion_cfg_parse_form`, with tests for missing, duplicate,
  out-of-range, non-digit and overlong fields, min >= max). Field names: `en`, `dmin`, `dmax`,
  `emin`, `tstart`, `tend`. The result page shows OK or the error. The change is logged old ->
  new.

### R6. Docs
`esp32/README.md` (motion detector, record type 4, CSV, settings, VERIFY: defaults on the
bench), `docs/decisions.md` (decisions 1-4 and the agent choices), `docs/architecture.md`,
`BACKLOG.md`: close "Radar motion detector"; add "Motion notifications outside the board"
(decision 4) and "Offline replay of the motion detector on recorded frames (host)".

## Non-goals
No own per-gate detector, no notifications, no protocol version bump, no change of the
LD2410C settings themselves, no offline replay tool.

## Acceptance
CI green; host tests (C and Python) pass; owner bench check: walking through the zone gives one
start and one end in `/log` and on the live page; standing still or moving outside the zone
gives none; settings survive a reboot; a recording contains the motion records and
`ld2410_rec.py export-csv --motion` lists them with plausible UTC times.
