# Spec: AERIS-10 Lite MVP on ESP32-S3 + HLK-LD2410C (and `firmware/` -> `stm32/`)

Date: 2026-10-02. Owner: Andrii. Status: approved in brainstorming (2026-10-02).

## Context

The real RF chain (ADAR1000/ADTR1107, LO PLL), the FPGA board and the 100 MSPS ADC are not
bought yet. The owner wants a working radar MVP from parts on the bench. The HLK-LD2410C is a
ready 24 GHz FMCW presence radar: it outputs target state, distances and per-gate energies over
UART. An ESP32-S3-DevKitC-1 (N32R8V, v1.1) is on hand.

## Decisions (owner, brainstorming 2026-10-02)

1. MVP = **ESP32-S3 + HLK-LD2410C**, no STM32, no FPGA. The STM32G0B1 firmware stays in the
   repo unchanged (frozen). Choice between "everything on ESP32-S3" (A) and "hybrid STM32 +
   ESP32-S3" (B) is postponed until the RF chain is bought.
2. FMCW of our own stays a BACKLOG option; the ESP32-S3 is chosen so that path stays open.
3. Framework: **ESP-IDF, C**. Separate top-level folder **`esp32/`**.
4. `firmware/` is renamed **`stm32/`**, with every path reference, CI and tests updated.
5. User interface: **web page served by the ESP32** (live view) **plus recording on the PC**.
6. Recording format: **raw LD2410C frames byte-for-byte** + frame number + ESP32 and PC time,
   binary file; CSV export from the raw file.
7. Live view sends **the latest snapshot at a fixed rate** (no queue); recording sends
   **batches** with frame numbers, a PSRAM ring buffer and resume after reconnect.
8. Wi-Fi: **STA with fallback AP**. AP WPA2 password random on first boot, kept in NVS,
   printed to the console. The Wi-Fi setup page is reachable **only through the AP**. Wi-Fi
   reset: hold BOOT >= 5 s while running (not at power-up: GPIO0 low at reset = ROM download
   mode).
9. Console and flashing through the **native USB** port (USB-Serial-JTAG, GPIO19/20); the
   UART-bridge connector of the owner's board was re-soldered and is not relied on.
10. First version: no LD2410C configuration (except enabling engineering mode at start), no
    GPS/IMU.

## Requirements

### R1. Rename `firmware/` -> `stm32/`
- `git mv firmware stm32`; update every reference outside `legacy/` and `docs/superpowers/`
  (CI, AGENTS.md, README.md, CONTRIBUTING.md, BACKLOG.md, docs/*.md, `stm32/README.md`,
  `stm32/tests/Makefile`, `fpga/README.md`, `tests/cross_layer/*`).
- `tools/check_paths.sh` also fails on a path reference to the old `firmware/` directory.
- No behaviour change: all STM32 gates (make test/make/DIAG=0/ADAR_COUNT=4), cross-layer tests
  and the CI job pass at the new path.

### R2. `esp32/` project layout
- ESP-IDF project, IDF version pinned (**v5.5.5**, latest v5.5 patch on Docker Hub
  2026-10-02), target `esp32s3`.
- Hardware-independent C modules (no ESP-IDF includes) in `esp32/components/core/`:
  `ld2410_parser` (byte stream -> frames), `ld2410_frame` (decode a data frame into fields),
  `ld2410_cmd` (encode command frames, decode ACK), `ringbuf` (frame ring buffer with sequence
  numbers), `rec_proto` (encode recording batches / parse client requests), `snapshot_json`
  (snapshot -> JSON text).
- Hardware-dependent code in `esp32/main/` (UART driver, Wi-Fi, HTTP/WebSocket, TCP recording
  server, NVS, BOOT button, mDNS, tasks).
- Host tests in `esp32/tests/` (`make test`, native gcc, `-Wall -Wextra -Werror`).
- `sdkconfig.defaults` committed; `sdkconfig` and `build/` git-ignored. No secrets in git.

### R3. LD2410C link
- UART1, **256000 8N1**, ESP32 GPIO18 = RX (from LD2410C TX), GPIO17 = TX (to LD2410C RX).
  LD2410C VIN from the DevKit 5V pin, GND common. OUT pin unused.
- Data frame (reference: Hi-Link LD2410C serial protocol; cross-checked against an open driver;
  engineering layout confirmed on hardware 2026-10-02, Hi-Link manual still not in
  `hardware/datasheets/`): header `F4 F3 F2 F1`, 2-byte little-endian payload
  length, payload, footer `F8 F7 F6 F5`. Payload: byte 0 data type (`0x01` engineering,
  `0x02` normal), byte 1 = `0xAA`, target state (0 none, 1 moving, 2 still, 3 both), moving
  distance cm (u16 LE), moving energy, still distance cm (u16 LE), still energy, detection
  distance cm (u16 LE); in engineering mode additionally max moving gate, max still gate,
  moving energy per gate 0..8, still energy per gate 0..8, then module-specific bytes; payload
  ends with `0x55`, `0x00`.
- Command frame: header `FD FC FB FA`, 2-byte LE length, 2-byte LE command word, value bytes,
  footer `04 03 02 01`. ACK: command word = command | `0x0100`, status u16 `0x0000` = OK.
  Engineering mode at start: enable configuration (`0x00FF`, value `0x0001`), enable
  engineering mode (`0x0062`), end configuration (`0x00FE`). Each ACK checked; on failure log
  and continue in normal mode (gates shown as unavailable).
- Parser requirements: resynchronises after garbage, rejects wrong footer / impossible length
  (max payload 64 bytes, VERIFY), handles frames split across reads and several frames in one
  read, never reads outside its buffer. Raw frame bytes are kept unchanged for recording.

### R4. Live view
- HTTP server on port 80 serves one page (HTML/CSS/JS embedded in the firmware, no external
  CDN). Page shows: presence state, moving / still distance and energy, detection distance,
  bars for 9 moving + 9 still gate energies (when in engineering mode), frame rate, link status.
- WebSocket `/ws` pushes the **latest snapshot** as JSON at **10 Hz**; a client that is slow
  gets only the newest snapshot (no per-client queue). Snapshot JSON includes the frame
  sequence number and ESP32 time.

### R5. Recording
- Every complete data frame gets a 32-bit sequence number and ESP32 time (µs since boot, u64)
  and is stored in a ring buffer in PSRAM (capacity 4 MiB, records variable-length).
- TCP server on port **5410**. Client sends a request `{magic, version = 2, from_seq}` (other
  versions: the server closes the connection); server sends batches about once per second:
  batch header `{magic, version, flags, first_seq, count, boot_id}` (`boot_id`: random per
  ESP32 boot, never 0, because the sequence restarts at 0 after a reboot) then records `{seq u32, esp_time_us u64, len u16, raw bytes}`. If `from_seq` is
  older than the oldest stored frame, the first batch has a `GAP` flag and starts at the oldest
  stored frame. All integers little-endian. Exact byte layout is fixed in the plan and in
  `esp32/README.md`; C and Python share test vectors.
- One recording client at a time; a new connection replaces the old one.

### R6. Wi-Fi
- On boot: if credentials are in NVS, connect as STA (timeout 15 s, retries in background);
  otherwise or on failure start AP `AERIS-MVP-XXXX` (last 2 MAC bytes), WPA2, password 12+
  random characters from the hardware RNG generated on first boot and stored in NVS. The AP
  password and the AP/STA IP are printed to the USB console at every boot.
- Setup page `/wifi` (scan list + SSID/password form, saves to NVS, reboots) is served only to
  clients on the AP interface; requests from the STA side get 404.
- mDNS host name `aeris-mvp` (`aeris-mvp.local`) on STA.
- BOOT button (GPIO0) held >= 5 s while running erases the stored STA credentials and reboots
  into AP. The AP password is kept.
- Credentials and the AP password are never logged except the AP password line, never sent to
  the live page, never in git.

### R7. Host recorder (`host/`, new files only)
- `host/ld2410_rec.py`: `record` (connect, write file, auto-reconnect resuming from last
  sequence, log gaps), `export-csv` (decode raw frames to CSV), `info` (frame count, duration,
  gaps).
- File format (version 2): file header `{magic, version, created UTC}` then records `{seq,
  esp_time_us, pc_time_ns, len, raw}`; gap markers and reboot markers `{old_boot_id,
  new_boot_id, pc_time_ns}` recorded. A changed `boot_id` resets the sequence baseline (no
  gap record, no dropping of "older" seqs); `info` reports reboots, `export-csv` emits
  `record=reboot` rows.
- Python LD2410C frame decoder mirrors the C decoder; both pass the shared vectors.
- Tests in `host/test_ld2410_rec.py` (pytest), including resume with a fake server.

### R8. CI
- New job "ESP32 MVP": `make -C esp32/tests test`, and `idf.py build` in container
  `espressif/idf:v5.5.5`. Python job runs the new pytest file. Existing jobs use `stm32/`.

### R9. Documentation
- `esp32/README.md`: hardware, wiring table, build/flash/monitor over native USB, first boot
  and AP password, Wi-Fi setup and reset, live page, recorder usage, protocol layouts,
  optional bench checks with the oscilloscope (LD2410C TX level 3.3 V, bit time ~3.9 µs at
  256000 Bd; 5 V ripple with Wi-Fi active).
- `docs/architecture.md`: MVP section; `docs/decisions.md`: decisions above;
  `BACKLOG.md`: LD2410C settings page, GPS NEO-6M / IMU BMI160, A-vs-B decision, PA
  over-temperature sensor choice, LD2410C manual into `hardware/datasheets/`;
  `AGENTS.md`/`README.md`/`CONTRIBUTING.md`: repo map and commands.

## Non-goals

- No change to STM32 firmware behaviour, RTL, or the existing host GUI/protocol.
- No LD2410C configuration UI, no GPS/IMU, no OTA update, no authentication on the live page.

## Acceptance

- CI green with the new job; path gate passes; host tests (C and Python) pass.
- Owner bench check: page shows live data from LD2410C over AP and over home Wi-Fi; a
  recording survives a Wi-Fi drop with no lost frames while the buffer covers the gap; CSV
  export opens; BOOT 5 s returns to AP.
