# Spec: GPS (NEO-6M) and IMU (BMI160) for the ESP32 MVP

Date: 2026-10-02. Owner: Andrii. Status: approved in brainstorming (2026-10-02).

## Context

The ESP32-S3 + HLK-LD2410C MVP (`esp32/`, merged in PR #6) records raw LD2410C frames with ESP32
time only. The owner has a GY-NEO6MV2 (u-blox NEO-6M) GPS and a GY-BMI160 6-axis IMU (no
magnetometer) on the bench.

## Decisions (owner, brainstorming 2026-10-02)

1. Goals: (1) UTC time and position in the recording, (2) GPS and tilt on the live page,
   (3) radar tilt (pitch/roll). Not now: azimuth/magnetometer, target map, motion detector.
2. No magnetometer in this cycle; IMU code written so one can be added later (BNO085 suggested
   if the owner orders one).
3. GPS and IMU go into the recording as **separate typed records** in the same stream
   (recording protocol **v3**); old v2 files stay readable by the recorder.
4. IMU in the recording at **10 Hz** (100 ms averages); internal sampling ~100 Hz. Rate is a
   single constant.
5. UTC source: **GPS, and SNTP when GPS has no fix** (STA mode with internet); every time sync
   records its source.
6. Tilt is **absolute** relative to the horizon; IMU-to-radar axis mapping is a firmware
   constant documented in the README. No "zero tilt" button in this cycle.
7. Future rotating radar / PPI display (owner idea): out of scope; noted in BACKLOG with the
   analysis: azimuth must come from the drive (stepper + homing or encoder), angular spacing is
   limited by the LD2410C 10 frames/s and its wide beam, not by the IMU rate.

## Requirements

### R1. Wiring (VERIFY against the boards)
- GY-NEO6MV2: VCC → 3V3, GND → G, module TX → **GPIO5** (UART2 RX), module RX → **GPIO4**
  (UART2 TX). 9600 8N1, factory configuration (no UBX configuration sent).
- GY-BMI160: VIN/3V3 → 3V3, GND → G, SCL → **GPIO9**, SDA → **GPIO8**, CS → 3V3 (I²C mode),
  SA0 → GND (address 0x68; firmware also probes 0x69). I²C 400 kHz.
- GPIO4/5/8/9 are not strapping, PSRAM, USB or LD2410C pins (VERIFY against the ESP32-S3
  datasheet / DevKitC-1 v1.1 pinout).

### R2. GPS
- Hardware-independent NMEA parser (C11, `esp32/components/core/`): line assembly from a byte
  stream, checksum validation, `RMC` (UTC time, date, status, lat/lon, speed, course) and `GGA`
  (fix quality, satellites, HDOP, altitude) for talker IDs `GP`/`GN`; empty fields mean "not
  valid"; bounded line length; invalid lines are dropped and counted.
- One `gps_fix` record per NMEA epoch (about 1 Hz), also without a fix (validity flags = 0), so
  the recording shows the fix state over time.
- Timing accuracy: no PPS on this board, so the ESP32 time stamp is taken at reception of the
  `RMC` sentence; the GPS-to-ESP32 time alignment is expected within about ±50–300 ms (VERIFY on
  the bench). A wired PPS is a BACKLOG improvement.

### R3. IMU
- BMI160 driver: chip-ID check, accelerometer ±4 g, gyroscope ±500 °/s, ODR 100 Hz (exact
  register values from the BMI160 datasheet, which must be added to `hardware/datasheets/`; until
  then VERIFY), read at ~100 Hz.
- Tilt (hardware-independent, C11, tested): complementary filter (gyro integration + accel
  gravity vector), pitch and roll in degrees, correct near ±90° and across ±180°; axis mapping
  constant.
- Every 100 ms an `imu` record: averaged raw accel (mg) and gyro (0.1 °/s) per axis, pitch and
  roll (0.01°), number of samples averaged.

### R4. Time
- `time_sync` record `{utc_unix_us, source}` (source 1 = GPS, 2 = SNTP); the record's
  `esp_time_us` is the matching ESP32 time. GPS sync on each valid `RMC` (time and date valid);
  SNTP (`pool.ntp.org`, ESP-IDF `esp_netif_sntp`) when STA is connected, sync records written on
  each SNTP sync. GPS takes priority while it has a fix.
- The host converts any record's `esp_time_us` to UTC with GPS priority (owner decision
  2026-10-02): a GPS `time_sync` of the same boot within +-2 s (`GPS_PRIORITY_WINDOW_US`) of
  the instant wins (the nearest such one); otherwise the nearest preceding `time_sync` of any
  source (fallback: the following one), same boot only.
- SNTP syncs are hourly by default, so once SNTP has synced the firmware re-emits an SNTP
  `time_sync` every 60 s (from an `esp_timer` callback, not the lwIP callback).
- RMC with status `V` is not used for `time_sync`; an RMC date before 2025 (week-rollover
  clone) is treated as time/date not valid.

### R5. Recording protocol v3 (exact layouts in the plan)
- Records become typed: `{seq u32, esp_time_us u64, type u8, len u16, payload}`; types
  `0 ld2410_frame` (raw LD2410C frame, as before), `1 gps_fix`, `2 imu`, `3 time_sync`.
  The `.ldrec` file additionally has `6 unknown` (a wire type the recorder does not know,
  kept instead of failing).
- One shared sequence for all types; GAP, keep-alive, `boot_id`, resume and reboot handling
  unchanged.
- File `.ldrec` v3 with matching record types; the recorder reads v2 and v3 files.
- `export-csv`: radar frames with extra columns (frame UTC, source, latest GPS fix, latest
  pitch/roll at the frame time); `--gps FILE` and `--imu FILE` write per-sensor CSVs.
  `info` adds GPS/IMU/time-sync statistics.
- C and Python share test vectors for every record type.

### R6. Live page
- WebSocket snapshot JSON gains `gps` (fix, sats, hdop, lat, lon, alt, speed, course, utc,
  time source) and `imu` (pitch, roll, status) objects; `null`/`not connected` when the sensor is
  absent or silent (> 3 s). The IMU counts as `error` when its last record is older
  than 1 s.
- New cards: GPS and Tilt (pitch/roll in degrees plus a simple level indicator), same style,
  tabular numbers, no jitter.

### R7. Robustness
- A missing or silent GPS/IMU never affects the LD2410C path; status visible on the page and in
  the 10 s log line. I²C errors are counted and retried with backoff.

### R8. Docs and BACKLOG
- `esp32/README.md` (wiring, no-fix behaviour, time accuracy, axis mapping), `docs/decisions.md`
  (decisions above), `docs/architecture.md`, `AGENTS.md` if commands change.
- BACKLOG: rotating radar + PPI display (analysis in decision 7), magnetometer / BNO085 azimuth,
  tilt zero button (with live-page authentication), radar motion detector, IMU recording at
  100 Hz, GPS PPS wiring.

## Non-goals

No azimuth, no magnetometer, no map, no rotation, no UBX configuration of the GPS, no change to
the LD2410C path or the Wi-Fi behaviour.

## Acceptance

CI green; host tests (C and Python) pass including v2 file compatibility; owner bench check:
GPS fix near a window/outdoors with correct position and UTC, SNTP time at home without fix,
tilt follows the board, recording with GPS/IMU and CSV export.
